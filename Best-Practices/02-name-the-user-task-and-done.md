# Name the user, the task, and done

An interface decision is ready to make when four things are named: who is doing the work, what they are trying to finish, the constraint the design has to respect, and the check that defines done.

## Include

- The user: the person in this situation, what they already know, and which abilities the flow has to support.
- The task: the outcome they can recognize as finished, in the words they would use.
- The constraint: time, attention, device, connectivity, policy, language, or the data the interface can actually show.
- The check: a usability check with a person, or a structured review of keyboard use, labels, contrast, and cues besides color.

## Leave in the product

Brand voice, campaign lines, screen-by-screen copy, the inventory of that product's screens, research recordings, and local design-tool files stay in the product. The four names above can travel. See [Separate practice from product](07-separate-practice-from-product.md).

## What done means

Done is the named check, run on the flow. A polished main-path screen is one state. The flow also includes empty, loading, error, and success. See [Design states with the main path](04-design-states-with-the-main-path.md).

## Size the decision

Decide one task at a time when the steps depend on each other. A request that mixes a new information architecture, a new visual hierarchy, and a new content model is hard to check and easy to leave half-specified.

## When the result misses

Add the missing name: the user you left out, the task you widened, the constraint you ignored, or the check you never ran. Another round of visual options, without saying which of the four was missing, produces another broad attempt.

## For a page in this repo

A documentation task names the decision, the reader (someone designing a later product), and the page to update. A new topic gets a new page. An existing topic is edited on its canonical page. See [Write searchable pages](08-write-searchable-pages.md).
